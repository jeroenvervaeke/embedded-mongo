# Contributing

Most of this repository is ordinary Rust. The exception is the MongoDB engine itself, which
takes hours to compile, so it is built once in CI and downloaded everywhere else. This file
covers that machinery: where the library comes from, what is cached, and how to publish a new
one. It also covers the one-time repair pass for directories an older engine damaged, because
testing that needs an engine no current checkout builds.

For using the library, see the [README](README.md). For why the engine is the size it is, see
[`docs/native-size-reduction.md`](docs/native-size-reduction.md).

## Where the engine comes from

`embedded-mongodb-sys/build.rs` resolves the native library on every build, first match wins:

| | |
| --- | --- |
| `EMBEDDED_MONGODB_NATIVE_LIB_DIR=<dir>` | Use `<dir>/libembedded_mongodb_native.so`, no questions asked. Emits a warning, because it outranks everything else with no checksum and no freshness check. |
| `EMBEDDED_MONGODB_BUILD_FROM_SOURCE=1` | Compile from the pinned submodule. Hours. |
| *(default)* | Download the library published for this target and verify it. |

A target with no published library is a hard error naming both alternatives. It never
silently falls back to a multi-hour Bazel build.

## Which binary a checkout downloads

Nothing is discovered at run time. `embedded-mongodb-sys/prebuilt.rs` is generated by CI,
committed, and read at build time:

```rust
const RELEASE_TAG: &str = "native-06cde4d5dd02";
const SOURCE_COMMIT: &str = "…";              // the commit CI built from
static PREBUILT: &[Prebuilt] = &[
    Prebuilt {
        target: "x86_64-unknown-linux-gnu",
        asset: "libembedded_mongodb_native-x86_64-unknown-linux-gnu.so",
        sha256: "…", size: 34_525_944, glibc_min: Some((2, 38)),
    },
    …
];
```

`TARGET` picks the row, `RELEASE_TAG` and `asset` build the URL, and `sha256` is the expected
digest. So the commit you check out decides which release and which exact bytes you get —
old commits keep resolving to the release they shipped with, forever.

**The digest comes from git, never from the network.** No `.sha256` is published beside the
binaries, deliberately: a digest sitting next to the file it describes proves nothing, since
whoever could replace one could replace both.

Verification runs on *every* build-script invocation, not only after a download, so a cache
entry truncated by a full disk is caught too. Size is checked before the hash, which is what
separates the two failures:

- wrong size → *"the download was truncated … re-run the build to retry"*
- right size, wrong bytes → *"the file is the expected size but not the expected bytes … It
  has not been used."*

There is no environment variable that skips verification.

## Caching

### The download cache

Content-addressed by digest, so two checkouts wanting the same bytes share one file and a
manifest bump can never collide with the entry it replaces:

```
$EMBEDDED_MONGODB_CACHE_DIR                 if set
$XDG_CACHE_HOME/embedded-mongodb            else, if set
~/Library/Caches/embedded-mongodb           macOS
~/.cache/embedded-mongodb                   Linux
<OUT_DIR>/cache                             no HOME; correct, just not shared
```

Deliberately **not** under `target/`, so `cargo clean` does not discard a 33 MB download.
Entries are installed by atomic rename, so concurrent cold builds cannot corrupt one another;
the worst case is a duplicated download. Interrupted downloads leave `.tmp-*` files, which
are swept after a day.

The library is symlinked into `OUT_DIR` on Linux. On macOS it is copied, because `LC_ID_DYLIB`
has to be rewritten to that path and the result re-signed — an unsigned arm64 dylib is killed
at load.

### Caches in CI

| what | where | key |
| --- | --- | --- |
| Downloaded library | `ci.yml`, every job that builds Rust | `native-lib-<target>-<hash of prebuilt.rs>` |
| Bazel bootstrap | `native.yml` build jobs | `bazel-bootstrap-<target>-<hash of .bazelversion, .bazeliskrc, MODULE.bazel.lock, uv.lock>` |

The bootstrap cache holds bazelisk, the uv cache and `mongo/python3-venv`. It exists because
`.bazelversion` pins a MongoDB *fork* of Bazel that ordinary bazelisk cannot resolve, and
because mongo's wrapper hook runs `uv sync` from PyPI on every cold invocation — a network
bootstrap on the critical path of a three-hour job. Both bazelisk paths are listed, since it
uses `Library/Caches` on macOS.

**There is deliberately no Bazel disk cache.** Its hit rate is lowest exactly when it would
help — any change worth building edits a central `BUILD.bazel` — while costing gigabytes
against a 10 GB repository-wide quota that is evicted LRU. The lever that matters is making
rebuilds rare, not making them fast.

## Releasing a new engine

### When you need to

Whenever anything the library is built from changes:

- the `mongo` submodule pin
- `patches/`
- `embedded-mongodb-sys/native/`
- `embedded-mongodb-sys/build_native.rs`

You do not have to notice this yourself. `build.rs` asks git three questions and refuses to
use a stale library, and `ci.yml`'s `prebuilt-freshness` job asks the same ones:

1. is the submodule at the commit the prebuilt was built from?
2. have any commits since `SOURCE_COMMIT` touched the paths above?
3. are any of those paths dirty?

Note that (2) is restricted to those paths — unrelated commits, docs and workflow changes do
not invalidate a manifest. Note also that a *patched* submodule working tree is expected and
is not treated as drift: applying the patches is a required step for a source build.

### How

```sh
gh workflow run native.yml --ref master -f publish=true
```

Dispatch only. A build runs for hours against a hard six-hour job cap, and publishing conveys
the work in object form under the SSPL — neither belongs on a push trigger. Omitting
`publish` gives a build-and-validate run across every target that publishes nothing, which is
what to use for a dry run.

### What it does, all of it automatically

1. **build**, one job per target, from the pinned submodule with the patches applied. Then,
   before anything is published: a per-target size band, an ELF version-need check on Linux
   (no `GLIBCXX`/`CXXABI`/`GCC_`, glibc no higher than 2.39), the Mach-O identity and
   signature on macOS, and a smoke test that loads the library and runs the whole suite.
   Android is checked against the NDK's own bionic stubs instead — every imported symbol has
   to resolve at the pinned API level, which is what a shared library never proves at link
   time — and the x86_64 ABI then runs the suite on an emulator.
2. **publish** — creates the release, uploads the libraries plus `LICENSE`, `NOTICE` and a
   `THIRD-PARTY-NOTICES` assembled from the actual link, then regenerates
   `embedded-mongodb-sys/prebuilt.rs` and pushes it as the GitHub App.
3. **verify** — re-tests the published artifacts on every target *through* the committed
   manifest, and builds the Python wheel to confirm the engine is vendored into it.

The wheel is built but never installed. `pymongo-embedded` is not published to PyPI and needs
PyMongo 4.18, which exists only as a `mongo-python-driver` checkout, so `pip install` would
resolve some unrelated release and fail on a difference that says nothing about this
repository. `./scripts/python` is how the binding is actually run; CI only checks the part
this pipeline owns, which is that a wheel built against the published library contains it.

`prebuilt.rs` is `@generated`. Never edit it by hand; the generator recomputes every digest
from the library itself rather than trusting the sidecar that came with it.

The manifest commit is pushed by a GitHub App, not with `GITHUB_TOKEN`. A push made with
`GITHUB_TOKEN` never triggers another workflow run, so `ci.yml` never saw that commit — the
least-reviewed commit in the repository — until somebody pushed again. An app's push is an
ordinary push, so `ci.yml` now runs on it.

That needs an app installed on the repository with `contents: write`, its id in the `APP_ID`
variable and its private key in the `APP_PRIVATE_KEY` secret. Both are read at the top of the
`publish` job, so a missing one fails before the release is created rather than after.

`verify` still runs. It overlaps with what `ci.yml` now does, and is kept because it is tied
to this release: it starts the moment the assets are published, on the ref that published
them, and its failure is this run's failure rather than a separate one nobody is watching.

### The release tag

Keyed on the engine's content, not on `HEAD`:

```sh
git ls-tree HEAD -- patches embedded-mongodb-sys/native \
    embedded-mongodb-sys/build_native.rs mongo | sha256sum | cut -c1-12
```

Identical engine inputs give an identical tag however many unrelated commits have landed, so
republishing the same engine finds the existing release and reuses its bytes instead of
minting a duplicate. Two releases holding byte-identical engines is what a `HEAD`-derived tag
produced before this.

**Never delete a release or replace an asset.** The build is not byte-reproducible — LTO
partitions in parallel and sandbox paths vary — so a deleted asset cannot be recreated, and
the committed digest would no longer match anything. The publish job is written to reuse an
existing release rather than overwrite it, and refuses outright if a tag exists with
different assets.

### Iterating on the steps after the build

The steps after the compile take seconds, and they are what usually fails. Rebuilding for
three hours to test a one-line change to them is waste:

```sh
gh workflow run native.yml --ref <branch> -f reuse_run=<run id>
```

That skips the compile, the swap file, the Bazel install, the patches and the bootstrap
caches, and takes the library and `stage/link.params` from that run's artifacts. Artifacts
are uploaded even when a later step fails — `if: always()` — precisely so a failure is
reusable. The submodule is still checked out, because the notices need the vendored licence
texts.

**Never publish from a reuse run.** A published library has to come from a build of the tree
it is published against.

## Third-party notices

The notices shipped beside the binaries are not a copy of MongoDB's. Theirs describes what
they distribute; this library links a different set — it drops what a server needs and an
embedded engine does not, and reaches a few things their release binaries never carry.

So `scripts/collect-third-party-notices` reads the Bazel link command itself, which lists
every object that went in, and fails if any linked component is unaccounted for.
`scripts/third-party-dispositions.tsv` records how each one is covered:

| | |
| --- | --- |
| `upstream <heading>` | Covered by a section in MongoDB's `THIRD-PARTY-NOTICES`; the section is checked to exist. |
| `append <path>` | Not covered there; its licence text is appended verbatim. |
| `absent <reason>` | Must not be in the link. Present means a build flag regressed. |
| `review <reason>` | Linked with no licence text available. Publishing is blocked. |
| `ours <path>` | This project's own code. |

Adding a dependency therefore fails the build until someone classifies it. That gate is why
`cpptrace` and `libdwarf` were found in the link with nothing covering them — `libdwarf` is
LGPL-2.1, which a stripped, LTO'd, version-scripted static library cannot satisfy — and why
`--//bazel/config:dev_stacktrace=False` now removes both.

## The one-time index repair pass

`src/repair/` is a migration over user data, not part of the engine. It exists because
`fix(engine): register databases already on disk at startup` fixed the engine and could not fix
the directories an older build had already damaged: those still hold documents that reached the
record store and no index. `Client::new` runs `validate`, and `validate {repair: true}` where
that reports errors or missing entries, once per directory. The README section *Repairing a
directory an older build damaged* is the user-facing half.

It lives in the Rust layer rather than in `embedded-mongodb-sys/native/` on purpose: a published
engine build stays exactly as published, the pass can be changed without a rebuild, and it can be
tested against a real damaged directory rather than through the engine's startup path.

Three decisions are worth knowing before changing it:

- **The marker is written only by a pass that visited every collection**, through a temporary
  file and a rename. A process that dies partway leaves no marker and the next open starts over;
  `validate {repair: true}` is idempotent, so an already-repaired collection validates clean and
  is left alone.
- **Nothing here may fail an open.** The alternative to a pass that could not run is the state
  every already-published build is in, whereas an open that refuses leaves the caller with no
  route to their data. Failures are reported through `tracing` and the client is returned. A
  directory the process cannot write to never reaches the pass at all: the engine's startup
  checkpoint panics and `fassert` aborts the process first, which
  `tests/durability/storage.rs` pins.
- **A collection still damaged after a repair does not hold the marker back.** Repeating a repair
  that did not work on every open would trade a data defect for a startup cost without fixing
  anything. It is reported at `WARN` and the pass moves on. A `validate` that *threw* is
  different, and is not a verdict at all: the engine catches everything but an interrupt, records
  it as a warning and still answers `ok: 1, valid: true`, so `Health::Inconclusive` exists to
  keep that from being read as a clean bill of health and marking the directory done.
- **`validate {repair: true}` has one destructive branch.** It deletes records whose BSON cannot
  be read, with no lost and found for them. That is not damage this defect produces, but the
  repair is the engine's general-purpose one and the trigger is any validation error, so
  `announce_deletions` reports it separately and the README says so.

### The damaged fixture

`tests/fixtures/damaged-reopen/` is a data directory a pre-fix engine produced, committed because
no current checkout can build an engine that would produce another. Each file is stored gzipped
on its own — the tables are mostly page padding, so the directory compresses by a factor of
twenty with no archive format to hand-roll — and `tests/repair/fixture.rs` documents what is in
it and why the journal and lock files are left out. `.gitattributes` marks the directory
`binary`, because none of those gzip streams happens to contain a NUL byte and git's own
detection would otherwise read them as text.

Regenerating it needs a library from before the fix:

```sh
EMBEDDED_MONGODB_NATIVE_LIB_DIR=<dir with a pre-fix libembedded_mongodb_native.so> \
  cargo run --release --example <a program that creates, closes, reopens and writes>
```

A pre-fix library is any entry in the download cache older than that commit; see
[Caching](#the-download-cache) for where they are. The directory the program leaves behind, minus
`journal/`, `_tmp/`, `mongod.lock` and `WiredTiger.lock`, is the fixture. `tests/repair/main.rs`
asserts against the exact document and index counts it holds, so replacing it means revisiting
those.

`tests/repair_skip.rs` is a separate target because `EMBEDDED_MONGODB_SKIP_INDEX_REPAIR` has to
be in the environment before anything opens an engine, and `set_var` is only sound while no other
thread can read the environment.

## Building the engine from source

Needed only when changing the engine. See the README for the toolchain requirements.

```sh
git submodule update --init --depth 1
./scripts/apply-mongo-patches
EMBEDDED_MONGODB_BUILD_FROM_SOURCE=1 cargo test --all-targets --release
```

**`--release` is not optional once the patches are applied.** Patches 0003, 0004 and 0006
leave dangling references to the code they remove, and only the release build's link-time
optimization and `--gc-sections` eliminate them. A debug build links — nothing checks for
undefined symbols there — and then fails to load.

Expect roughly two and a half to three hours per target on a CI runner, and note that the
whole-program LTO phase runs after every object is compiled and peaks near 16 GB, which is
why the Linux CI jobs add swap.

## Supported targets

Prebuilt libraries are published for `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`,
`aarch64-apple-darwin`, `aarch64-linux-android` and `x86_64-linux-android`. Anything else
builds from source.

Both Android libraries cross-compile from the x86_64 Linux runner with the NDK, against
bionic at the API level `embedded-mongodb-sys/build_android.rs` pins. Bazel is told the
target platform is `@platforms//os:linux` — Android is a Linux kernel with a different libc,
and every `select()` in the engine and its third-party tree is written against `os:linux` —
and `patches/0007-build-for-android.patch` covers what bionic and libc++ do not provide.
`patches/0008-guard-a-null-shared-object-name-on-bionic.patch` covers the other direction:
bionic hands `dl_iterate_phdr` callbacks a null object name where glibc passes the empty
string, and the stack-trace machinery took that on trust — a segfault as the library loads
on Android releases before 9.0, which is below the `minSdk` the AAR advertises.

Intel macOS is absent because that runner never finished a build inside the six-hour job cap,
and GitHub retires the image in August 2027. Windows is tracked in
[issue #9](https://github.com/jeroenvervaeke/embedded-mongo/issues/9). Adding a target is one
entry in the `native.yml` matrix plus a republish; nothing in the design assumes a fixed set.
